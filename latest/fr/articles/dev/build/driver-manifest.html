Manifeste des pilotes

Chaque noyau Cosmos reçoit deux fichiers générés par Cosmos.Kernel.SourceGenerators : le point d'entrée et le manifeste des pilotes. Cette page décrit le manifeste : ce qu'écrivent les deux générateurs, quelles classes [Driver] le build enregistre et dans quel ordre, comment un commutateur de fonctionnalité conditionne un enregistrement, comment un projet de noyau écarte un pilote ou en inclut un explicitement, et ce que signale le générateur lorsqu'il ne peut pas faire ce qu'une classe demande ; la plomberie du build, les règles de visibilité et les tests qui se trouvent derrière le manifeste ferment la page. Pour savoir à quel moment de la séquence de démarrage le manifeste s'exécute, voir Démarrage du noyau.

Le manifeste existe parce que rien d'autre ne peut trouver un pilote. Un noyau est compilé à l'avance et le code du noyau n'utilise pas la réflexion : le noyau ne peut donc pas chercher les classes de pilotes dans ses assemblies au démarrage, et le trimming exclut de l'image toute classe qu'aucun code ne référence. Le manifeste est le code qui référence chaque pilote : un générateur de source l'écrit au moment du build à partir des classes [Driver] qu'il trouve et de la politique du projet, et un pilote qu'il ne construit pas n'est pas dans le noyau. Son ordre compte aussi, comme dernier critère lorsque le kit choisit entre plusieurs pilotes pour un périphérique. Ces notions, ainsi que les notions matérielles sur lesquelles s'appuie un pilote, sont expliquées dans le glossaire des pilotes, et Écrire un pilote présente le kit du point de vue de l'auteur de pilote.

Ce qui est généré

Chaque fichier a son propre générateur. CosmosEntryPointGenerator écrit le point d'entrée à partir de la seule propriété CosmosKernelClass, si bien que modifier les sources du noyau ou sa politique de pilotes le laisse en cache ; DriverManifestGenerator écrit le manifeste à partir des pilotes qu'il trouve et de la politique. Lorsque la propriété est vide, aucun des deux fichiers n'est généré. Lorsqu'elle est définie, le point d'entrée appelle toujours le manifeste en premier. L'appel est explicite, et non un initialiseur de module, si bien que les pilotes sont enregistrés dans l'ordre du manifeste, juste avant le démarrage du noyau. Les deux fichiers sont présentés ici sans leurs commentaires de documentation ni leurs attributs [GeneratedCode] :

// <auto-generated/> CosmosEntryPoint.g.cs
namespace Cosmos.Kernel.System.Internal;

public static class CosmosEntryPoint
{
    public static void Main()
    {
        global::Cosmos.Kernel.System.Internal.DriverManifest.Register();
        global::Cosmos.Kernel.System.Internal.KernelEntry.Start(new global::MyOS.Kernel());
    }
}

// <auto-generated/> DriverManifest.g.cs
// The driver registry is on the experimental driver kit seam (COSMOS0003).
// This file is generated, so it acknowledges the seam for itself alone;
// a driver this kernel declares still meets the diagnostic in its own code.
#pragma warning disable COSMOS0003
namespace Cosmos.Kernel.System.Internal;

internal static class DriverManifest
{
    public static void Register()
    {
        global::Cosmos.Kernel.HAL.DriverKit.DriverRegistry.Register(new global::MyOS.Drivers.BoardDriver());
        if (global::Cosmos.Kernel.System.KernelFeatures.Network)
        {
            global::Cosmos.Kernel.HAL.DriverKit.DriverRegistry.Register(new global::Acme.Drivers.AcmeNicDriver());
        }
    }
}

Le manifeste contient un appel Register par pilote, chacun construisant le pilote avec son constructeur sans paramètre. Il est généré même lorsqu'aucun pilote ne subsiste, avec un corps de Register vide. Le registre qu'il appelle se trouve sur le point d'extension expérimental du kit, et les pilotes livrés avec Cosmos placent un appel dans le manifeste de chaque noyau, si bien que le fichier commence par désactiver, pour lui seul, l'identifiant de diagnostic du point d'extension : l'auteur du noyau ne l'a pas écrit, et un noyau qui n'a pas supprimé cet identifiant (voir Visibilité) compile quand même.

Lorsque EmitCompilerGeneratedFiles est activé, ce que Cosmos.Sdk fait par défaut, les deux fichiers sont écrits sous le répertoire intermédiaire, un dossier par générateur :

$(IntermediateOutputPath)/generated/Cosmos.Kernel.SourceGenerators/
    Cosmos.Kernel.SourceGenerators.CosmosEntryPointGenerator/CosmosEntryPoint.g.cs
    Cosmos.Kernel.SourceGenerators.DriverManifestGenerator/DriverManifest.g.cs

Lire DriverManifest.g.cs à cet endroit est le moyen le plus rapide de vérifier quels pilotes un noyau embarque.

Comment les pilotes sont trouvés

Un pilote est une classe marquée [Cosmos.Kernel.HAL.DriverKit.Driver]. Le générateur cherche à deux endroits et garde leur ordre fixe, car la position dans le manifeste est le dernier critère d'arbitrage lorsque deux pilotes de même priorité et de même spécificité correspondent au même périphérique (correspondance des pilotes) :

Source Classes retenues Ordre
Le projet de noyau lui-même Toute classe marquée que l'assembly peut construire depuis son niveau supérieur (une classe imbriquée privée est signalée par COSMOSGEN001 et écartée) Par chemin de fichier (ordinal), puis par position dans le fichier
Les assemblies référencés qui référencent Cosmos.Kernel.HAL (ou qui sont cet assembly) Les classes marquées que l'assembly du noyau peut voir : les publiques, et les internes couvertes par un octroi InternalsVisibleTo Par nom d'assembly, puis par nom de type complet, tous deux en ordre ordinal

Les pilotes propres au noyau viennent en premier, puis ceux des assemblies référencés. Un assembly qui ne référence pas Cosmos.Kernel.HAL n'est pas parcouru, puisqu'il ne peut pas porter l'attribut.

Pour être enregistrée, une classe doit être concrète (ni abstraite, ni statique) et non générique, dériver de Cosmos.Kernel.HAL.DriverKit.Driver et avoir un constructeur sans paramètre que l'assembly du noyau peut appeler. Une classe marquée qui ne remplit pas l'une de ces conditions est signalée (COSMOSGEN001) et écartée.

Les pilotes livrés avec Cosmos suivent le second chemin. Ils se trouvent dans Cosmos.Kernel.Drivers, que porte l'agrégateur Cosmos.Kernel référencé par chaque noyau : les vingt-cinq figurent donc dans le manifeste de chaque noyau, après ses propres pilotes, sans que le noyau référence lui-même le package. Ils sont triés par nom de type complet, et le nom complet d'un pilote livré contient son type de bus, sa catégorie et son dossier de pilote (Cosmos.Kernel.Drivers.Pci.Storage.Nvme.NvmeDriver), si bien que cet ordre les regroupe par type de bus (Pci, Platform, Ps2, Usb, Virtio) puis, au sein d'un même type, par catégorie. Vingt-deux d'entre eux sont enregistrés sous une garde de fonctionnalité, et trois sans aucune :

Fonctionnalité Pilotes
Pci PciHostDriver, PcieRootPortDriver, VirtioPciTransportDriver
Network E1000EDriver, VirtioNetDriver
Graphics VirtioGpuDriver, VmwareSvgaDriver, AmdDcnDriver, IntelGraphicsDriver
Storage AhciDriver, NvmeDriver, VirtioBlkDriver
Audio HdAudioDriver
Usb XhciDriver, EhciDriver, OhciDriver, UsbHubDriver, UsbKeyboardDriver, UsbMouseDriver, UsbMassStorageDriver
Keyboard Ps2KeyboardDriver
Mouse Ps2MouseDriver
Aucune VirtioMmioTransportDriver, VirtioInputDriver, I8042Driver

Gardes de fonctionnalité

[Driver(Feature = DriverFeature.Network)] rattache l'enregistrement à un commutateur de fonctionnalité. Le générateur enveloppe l'appel Register dans un if portant sur la propriété de même nom de Cosmos.Kernel.System.KernelFeatures, une propriété par if et rien d'autre dans la condition, ce qui est la forme qu'ILC réduit à une constante. Un noyau qui met CosmosEnableNetwork à false ne construit alors jamais le pilote, et comme rien d'autre ne construit un pilote livré, tout ce que seul ce pilote référence est éliminé avec lui par le trimming.

Les membres de l'énumération DriverFeature reprennent par leur nom les propriétés de KernelFeatures (Interrupts, Uart, Pci, Timer, Keyboard, Mouse, Network, Storage, Fat, Graphics, Scheduler, Usb, Audio), et None n'émet aucune garde. Le générateur résout la propriété dans la compilation du noyau, si bien qu'un membre sans propriété donne une erreur de build (COSMOSGEN003) plutôt qu'un manifeste qui ne compile pas. FeatureParityTests, dans tests/Cosmos.Tests.SourceGenerators, maintient les deux listes en phase.

Exclure et inclure explicitement

Un projet de noyau façonne son manifeste, sa politique de pilotes, avec deux types d'éléments :

<ItemGroup>
  <!-- Drop a driver the build would otherwise register. -->
  <CosmosDriverExclude Include="Acme.Drivers.AcmeNicDriver" />
  <!-- Register a driver declared [Driver(Default = false)]. -->
  <CosmosDriverInclude Include="Acme.Drivers.ExperimentalGpu" />
</ItemGroup>

Les noms sont des noms de type complets sous leur forme C#, sans global::, les types imbriqués étant joints par des points (MyOS.Drivers.Bus.Child). Un pilote livré s'exclut de la même façon, par son nom de type complet : <CosmosDriverExclude Include="Cosmos.Kernel.Drivers.Pci.Network.E1000E.E1000EDriver" /> tient le pilote Intel hors du manifeste.

Un pilote exclu est écarté quelle que soit sa valeur Default, et un pilote avec Default = false n'est enregistré que lorsqu'un élément CosmosDriverInclude le nomme. Un élément qui ne correspond à aucune classe [Driver] visible du noyau est signalé (COSMOSGEN002) : c'est ainsi qu'une entrée périmée ou mal orthographiée se révèle. La politique est appliquée avant la validation, si bien qu'un pilote que le noyau exclut ou n'inclut pas explicitement n'est jamais signalé, et les diagnostics ci-dessous portent sur ce que le manifeste enregistrerait.

Diagnostics

Le générateur signale trois diagnostics, tous dans la catégorie Cosmos.DriverKit :

Id Gravité Signification
COSMOSGEN001 Avertissement Une classe [Driver] est écartée : elle est abstraite, statique ou générique, ne dérive pas de Driver, n'a pas de constructeur sans paramètre que l'assembly du noyau peut appeler, ou n'est pas accessible depuis l'assembly du noyau. Le message indique la raison.
COSMOSGEN002 Avertissement Un élément CosmosDriverExclude ou CosmosDriverInclude ne correspond à aucune classe [Driver] visible du noyau.
COSMOSGEN003 Erreur Un [Driver] nomme un membre de DriverFeature sans propriété KernelFeatures de ce nom, si bien que l'enregistrement ne peut pas être conditionné.

Les règles sont listées dans src/Cosmos.Kernel.SourceGenerators/AnalyzerReleases.Unshipped.md, au format de suivi des versions qu'attend le package des analyseurs Roslyn.

Plomberie du build

Un générateur ne lit que les propriétés de build que le projet lui rend visibles (générateurs de source). Ces générateurs en lisent trois, rendues visibles par des éléments CompilerVisibleProperty dans Cosmos.Kernel.SourceGenerators.props, qui est livré dans le package du générateur. Le générateur du point d'entrée ne lit que CosmosKernelClass, et celui du manifeste lit les trois :

Propriété Définie par Lue sous la forme
CosmosKernelClass Le projet de noyau, ou Sdk.props à partir de RootNamespace build_property.CosmosKernelClass
CosmosDriverExcludeList La cible CosmosCollectDriverPolicy de Sdk.targets, qui joint les éléments CosmosDriverExclude build_property.CosmosDriverExcludeList
CosmosDriverIncludeList La même cible, qui joint les éléments CosmosDriverInclude build_property.CosmosDriverIncludeList

Deux détails de cette cible comptent pour quiconque la modifie. Les éléments sont joints dans une cible plutôt que dans un PropertyGroup lu au moment de l'évaluation, car une référence d'élément n'y est pas développée, et la cible s'exécute avec BeforeTargets="GenerateMSBuildEditorConfigFileCore", l'étape qui écrit l'editorconfig du compilateur. Le séparateur est une virgule, car le compilateur lit ce fichier comme un editorconfig, où un point-virgule commence un commentaire : une liste jointe par des points-virgules serait donc coupée après son premier nom.

Visibilité

Le kit est public, sous le point d'extension expérimental COSMOS0003 : Driver, DriverAttribute, DriverRegistry et tous les autres types sous Cosmos.Kernel.HAL.DriverKit portent [Experimental("COSMOS0003")]. Un noyau ou une bibliothèque qui déclare une classe [Driver] supprime donc cet identifiant dans son .csproj, et une bibliothèque de pilotes se déclare en plus assembly de pilotes :

<PropertyGroup>
  <NoWarn>$(NoWarn);COSMOS0003</NoWarn>
  <!-- A class library of drivers only: held to the public surface by the analyzer. -->
  <CosmosDriverAssembly>true</CosmosDriverAssembly>
</PropertyGroup>

Un noyau qui ne déclare aucun pilote propre n'a besoin d'aucune suppression. Le manifeste généré désactive l'identifiant pour lui-même, puisque l'auteur du noyau ne l'a pas écrit, et c'est le seul endroit où un tel noyau nomme le kit ; la suppression concerne le code de pilote que déclare un noyau ou une bibliothèque. Écrire un pilote présente le kit et les lignes de projet du point de vue de l'auteur de pilote, et Suivi de l'API publique décrit ce à quoi un assembly de pilotes est tenu.

Tests

tests/Cosmos.Tests.SourceGenerators exécute les deux générateurs sur l'hôte contre des compilations en mémoire, avec des stubs à la place du kit et de l'anneau, et vérifie à l'identique le texte généré et les diagnostics. CachingTests vérifie qu'ajouter un pilote régénère le manifeste et laisse le point d'entrée en cache. La suite s'exécute seule avec :

dotnet test tests/Cosmos.Tests.SourceGenerators -c Debug

La CI l'exécute en tant que job source-generator-tests de .github/workflows/dotnet.yml.
