中断上下文

当设备发出中断时，CPU 会在下一个指令边界处停止正在运行的代码，并跳转到一个处理程序。处理程序不是线程：它借用被它中断的代码的栈，并在中断被屏蔽的状态下运行，因此在它返回之前，该 CPU 上不会运行任何其他代码，就连驱动抢占的定时器节拍也不例外。处理程序运行在中断上下文中，其余一切都运行在线程上下文中。

因此，处理程序不能等待。等待意味着把 CPU 让给另一个线程，而处理程序没有可以挂起的线程：一个睡眠、等待事件，或者在被中断代码持有的锁上自旋的处理程序，会永远等下去。内核把中断工作一分为二。上半部（top half）在处理程序中运行，负责确认设备的中断并唤醒等待者。下半部（bottom half）稍后在线程上下文中运行，在那里它可以阻塞，也可以获取普通的锁。

处理程序与线程共享的数据需要一个在持有期间禁用中断的自旋锁，否则处理程序可能在持有者所在的 CPU 上触发，并永远自旋等待一个在处理程序返回之前都无法运行的线程。这样的锁只能短暂持有，绝不能跨越等待。

在驱动工具包中，处理程序通过它的寄存器窗口确认中断，并通过它的 InterruptContext 移交工作：Mask() 屏蔽它的中断源，Signal(DeviceEvent) 唤醒一个正在等待的线程，Schedule(WorkItem) 把下半部排入工具包工作线程的队列，而 DeviceLock.Acquire() 就是那个禁用中断的自旋锁。防护机制会捕获对 DeviceBinding 方法以及部分访问对象成员（例如 UsbAccess 传输和 Ps2Access.TryCommand）的调用：在真实中断中，它会让内核停机并指出该成员的名称；在合成分派中，它会抛出异常，此时工具包记录这个故障并屏蔽该中断源。

工具包还加了一条自己的规则：驱动程序的处理程序不能分配内存。内核自己的处理程序会分配内存，垃圾回收器也能容忍；这是一条安全规则，因为分配可能牵涉到在中断上下文中行为异常的运行时机制，尤其是接口分派解析和异常抛出。没有任何机制检测内存分配：防护机制只在这些工具包成员内部运行，从不在驱动程序自己的代码中运行。参见两种执行上下文与防护机制、工作项和设备锁。
