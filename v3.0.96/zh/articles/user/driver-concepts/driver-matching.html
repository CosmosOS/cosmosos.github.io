驱动程序匹配

内核带有许多驱动程序，也会遇到许多设备，总得有某种机制来决定哪个驱动程序服务哪个设备。内核不能让每个驱动程序都去试探每个设备、看自己是否认得它，因为一块芯片用来表示状态的寄存器，在另一块芯片上可能会启动一条命令。因此每个驱动程序都事先声明自己服务什么，形式是一张匹配表：每个表项列出总线为设备报告的标识字段，例如 PCI 厂商 ID 和设备 ID 或类别字节、USB 接口类别，或者来自固件描述的 compatible 字符串（总线）。设备出现时，内核把它的标识与每一张表比较，只有含有合适表项的驱动程序才会得到这个设备，一次一个，在探测（probe）中进行：探测是驱动程序查看硬件、决定接管还是拒绝它的机会。

同一个设备常常有多个驱动程序都能匹配。通用驱动程序匹配一整个类别，例如所有 xHCI 控制器，而另一个驱动程序匹配它更了解的某块芯片的确切设备 ID，内核作者编写的驱动程序也可能与内核已经内置的驱动程序匹配相同的 ID。内核用一个优先顺序来解决这个问题。更具体的匹配排在更通用的匹配之前，因为指明确切芯片的驱动程序比只指明其类别的驱动程序更了解它。显式的等级让一个驱动程序无论匹配情况如何都能排到其他驱动程序前面，替代驱动程序正是这样胜过内置驱动程序的。最后一个键用来打破剩下的平局。第一个探测接受设备的候选者保留该设备，拒绝则把设备交给下一个候选者。

陷阱在于平局被偶然打破。如果最后一个键是加载顺序、哈希顺序，或者文件恰好被编译的顺序，那么在添加一个无关的驱动程序或重命名一个文件时，绑定某个设备的驱动程序就可能改变，同一份源代码的两次构建也可能表现不同。最后一个键必须是确定性的，并且对想弄清某个设备为何归属某个驱动程序的人可见。拒绝也必须让设备保持下一个候选者所预期的状态，因为在拒绝之前打开了某些东西的探测，会让下一个驱动程序接手一个处于并非自己所选状态的设备。

在驱动工具包中，驱动程序的 Matches 是一个 DeviceMatch 列表，每一项都有一个 Specificity，即它检查的标识字段数。一个节点的候选者先按 Priority 排序（从高到低），再按其最佳匹配的特异性排序（从高到低），最后按清单位置排序（从前到后），第一个返回 ProbeResult.Bound 的候选者保留该节点。每个内置驱动程序都把 Priority 保留为 0，所以替代驱动程序只需要一个更高的值。清单位置在构建时确定：内核自身的驱动程序排在最前，先按文件路径、再按在文件中的位置排序，之后是被引用程序集中的驱动程序，先按程序集名称、再按完整类型名排序。启动日志会列出每个节点的候选者及其 prio 和 spec，工具包在把节点提供给下一个候选者之前，会释放拒绝的探测所获取的一切资源。参见标识与匹配和如何找到驱动程序。
