Spinlocks et masquage des interruptions

Un spinlock protège des données contre du code qui s'exécute sur un autre CPU : un thread qui trouve le verrou pris tourne en boucle jusqu'à ce que son détenteur le relâche. Cela fonctionne parce que le détenteur continue de s'exécuter sur son propre CPU pendant que l'autre tourne en boucle. Cela ne fonctionne pas contre un gestionnaire d'interruption sur le même CPU. Si ce gestionnaire d'interruption se déclenche alors que le code qu'il a interrompu détient le verrou, et qu'il tente de prendre le verrou lui-même, il tourne en boucle, et le détenteur ne peut pas relâcher le verrou avant le retour du gestionnaire d'interruption, si bien que le CPU tourne en boucle indéfiniment.

Le code qui partage des données avec un gestionnaire d'interruption masque donc les interruptions sur son CPU autour de chaque accès, afin que le gestionnaire d'interruption ne puisse pas se déclencher au milieu de celui-ci. Le masquage est la seule protection dont un CPU a besoin contre ses propres interruptions, mais un spinlock reste nécessaire contre les autres CPU, c'est pourquoi les noyaux combinent les deux dans un verrou sûr vis-à-vis des interruptions : masquer, puis prendre le verrou ; relâcher, puis restaurer. Le masquage sauvegarde l'état précédent des interruptions et le restaure, au lieu de réactiver les interruptions, de sorte qu'une section masquée peut s'imbriquer dans une autre.

Le piège, c'est le code qui ne prend aucun verrou. Un verrou n'exclut que le code qui prend ce même verrou, et un gestionnaire d'interruption qui touche aux données sans le prendre, souvent parce qu'il n'a pas le droit d'attendre, n'est écarté par aucun verrou que détient le côté thread. Seul le masquage écarte ce gestionnaire d'interruption. Le masquage ne rend par ailleurs atomique qu'une section, et une seule : un appelant qui lit un nombre d'éléments dans un appel masqué puis parcourt les éléments dans d'autres appels peut voir la structure changer entre ces appels.

Dans l'ordonnanceur de Cosmos, le chemin du tick ne prend absolument aucun verrou : OnTick s'exécute dans l'interruption du minuteur et PickNext dans la sortie d'interruption, quelle qu'elle soit, qui réordonnance, et tous deux comptent sur le fait que les interruptions y sont masquées. Le gestionnaire appelle les hooks du cycle de vie des threads et les deux hooks par CPU avec les interruptions masquées, de sorte que le tick ne peut pas survenir au milieu de l'un d'eux. SchedulerManager.SetPriority détient un spinlock par CPU pris sans masquage, qui écarte un second appelant mais pas le tick, et GetPriority, GetRunQueueCount et GetRunQueueThread sont appelés sans aucune protection. Ces quatre hooks, et tout point d'entrée qu'une politique ajoute elle-même, masquent les interruptions avec SchedulerManager.MaskInterrupts(), dont le InterruptMaskScope restaure l'état précédent lorsqu'il est libéré, si bien que masquer à l'intérieur d'un hook déjà masqué est sans danger.
