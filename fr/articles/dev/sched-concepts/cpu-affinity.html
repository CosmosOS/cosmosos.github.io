Affinité CPU et répartition de charge

Sur une machine à plusieurs CPU, un ordonnanceur donne en général à chaque CPU sa propre file d'exécution. Une file unique partagée exigerait un verrou que tous les CPU se disputeraient à chaque changement, et un thread qui revient sans cesse sur le même CPU y retrouve ses données encore présentes dans les caches de ce CPU. Les files par CPU entraînent deux décisions qui leur sont propres. Le placement choisit un CPU pour un thread lorsqu'il est créé ou réveillé, généralement le moins chargé. La répartition de charge déplace ensuite les threads, quand une file s'allonge alors qu'un autre CPU reste inactif : le CPU inactif tire, ou vole, un thread à un CPU occupé, ou bien un CPU occupé en pousse un ailleurs.

L'affinité limite les endroits où un thread peut aller. L'affinité stricte, ou épinglage, restreint un thread à un CPU ou à un ensemble de CPU, pour un thread par CPU comme un thread inactif, ou pour du code qui touche à un état par CPU. L'affinité souple n'est qu'une préférence : un cache encore chaud, qu'un ordonnanceur met en balance avec la charge.

Le piège, c'est l'état par CPU qui voyage avec le thread. Une politique qui tient une horloge par CPU, comme le temps virtuel d'un ordonnanceur à partage équitable, doit recaler un thread qui migre sur l'horloge de la destination, faute de quoi le thread arrive très en avance ou très en retard sur tous les threads qui s'y trouvent. Une migration touche aussi les files de deux CPU à la fois : elle doit donc être sûre vis-à-vis des ticks des deux, et un répartiteur de charge ne doit jamais voler un thread épinglé.

Dans Cosmos, le noyau s'exécute aujourd'hui sur un seul CPU. Les hooks qui placent et répartissent les threads, SelectCpu et Balance, n'ont aucun appelant, et OnThreadMigrate ne s'exécute que lorsque le Balance propre à une politique l'appelle. La conception est malgré tout par CPU : chaque hook qui touche à une structure d'exécution reçoit le PerCpuState sur lequel il opère, une politique garde sa structure d'exécution dans le SchedulerData de cet état, et SchedulerThread.CpuId désigne le CPU auquel un thread est attribué, si bien qu'une politique écrite par CPU dès maintenant restera valable telle quelle. SchedulerThreadFlags.Pinned marque un thread qui ne doit pas migrer ; seuls les threads inactifs le portent, puisqu'un noyau peut lire les indicateurs d'un thread mais pas les modifier. Le Balance de Stride vole le thread de queue de la file la plus longue quand sa propre file est vide et que cette file contient plus d'un thread, sauf si ce thread de queue est épinglé, et son OnThreadMigrate recale le Pass du thread sur le GlobalPass de la destination augmenté du Remain sauvegardé du thread.
